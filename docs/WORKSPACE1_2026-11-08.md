## 使用形态

1. TUI 设置页进入“编辑工作区”，填写实例共享 roots，每个目录明确 key、label、绝对 path 和 read_only / read_write；保存仅形成草稿。
2. 点“应用工作区”，绑定刚才保存的摘要。所有已绑定插件加载同一目录快照；状态为应用中时尚不能声称全部运行副本已更新。
3. 首次绑定时，在知识插件配置中用 `workspace_binding: "instance"` 替代 roots；文件插件同样绑定，同时保留位于资料根外的 `state_directory`。分别保存并应用一次插件配置。后续目录变更只操作统一工作区。
4. 知识插件配置或工作区目录变化并应用后，后台自动建立索引。不需要再到对话中下发 `knowledge.reindex`。保存但未应用不触发；匹配当前配置的 READY 索引直接复用。
5. 已保存、配置待生效、配置已生效与索引 INDEXING / READY / FAILED 分开。TUI 的配置 APPLIED 不是索引完成证明；知识概览提供实际索引状态和固定诊断码。失败不无限重试，修正配置后再应用；手动 reindex 保留为补救入口。

工作区示例（示例路径需要本人替换，不会自动创建或授权）：

```json
{
  "workspace_id": "instance",
  "roots": [
    {"key": "personal", "label": "个人资料", "path": "D:/AssistantDocuments", "mode": "read_write"}
  ]
}
```

知识插件配置示例：
```json
{"workspace_binding": "instance", "embedding": {"provider": "none"}}
```
文件插件配置示例：
```json
{"workspace_binding": "instance", "state_directory": "C:/AssistantData/file-state"}
```

## 实现边界

- 宿主统一保存目录授权；插件保留自己的业务配置。`RuntimeContext.workspace` 提供 workspace_id、revision、roots；宿主没有具体业务扩展 ID 分支。候选版本为 personal.files 0.1.1 与 personal.knowledge 0.1.7。
- 旧 roots 配置继续可用，不静默迁移、不默认向所有插件授权。明确绑定后禁止并存 roots，缺失或撤销授权时不得回退旧目录。聊天中提到任意路径仍不会新增授权。
- 本机工作区接口仅回环并要求工作台专用请求头，拒绝浏览器 Origin；保存与摘要 CAS 应用分离。控制配置、扩展载荷、凭据目录、日志、备份和索引状态不放入可写资料根。
- 同一工作区修改产生新修订；A→B→A 不能复活旧文件写入计划。已在途调用不被自动重放；旧读取跨修订不作为当前资料返回，外部 UNKNOWN 历史保留。旧任务工具快照不被静默改写。
- 知识自动索引由插件实现，跨 Admin/Agent 副本通过数据库单一构建租约协调。配置指纹包含目录、工作区修订、扫描选项和 embedding 配置；失败保留明确状态，不以空结果冒充没有资料。
- 索引构建的数据写入需要同事务租约栅栏；失去租约的旧扫描不能改写后继索引。扫描、抽取等耗时文件 IO 不阻塞 Worker 事件循环，关闭时取消并回收后台任务。
- 文件删除仍只允许本人终端确认；绑定模式的 CLI 增加 `--workspace-state` 指向宿主 `var/workspace/.applied/instance.workspace.json`，`--config` 指向插件的已应用快照。两份权威文件在确认前后重读，不使用导出的副本；修订或文件哈希变化拒绝旧计划。
- 本轮不实现多项目切换、虚拟文件系统、复杂权限继承或工作区备份。稳定标识、修订与公开 SDK 是后续扩展点，不承诺这些功能已经实现。扩展仍是以本机用户权限运行的可信代码，进程和 venv 不是恶意代码沙箱。
